# AI eval: plain-English search

**What is evaluated:** the AI service's search. It turns a reader's question into typed
filters (`SearchPlan`: genre, read status, minimum rating, trope, author/title text) and
then returns the matching books. A wrong filter means the wrong books, so the headline
metric is whether the **right books** come back.

**How:** [`run_eval.py`](run_eval.py) runs the real Pydantic AI agent from `ai-service/`
over the 26 cases in [`dataset.jsonl`](dataset.jsonl). That's the same instructions,
`list_my_tropes` tool, output validator, retries and limits as production. It uses
[pydantic-evals](https://ai.pydantic.dev/evals/) for the run and custom evaluators for
scoring. Every model sees the same in-memory copy of the seeded `demo` vault (16 books,
22 tropes), so only the model differs. Raw per-case results are in [`results/`](results/).

**Scoring** (deterministic, no LLM judge, since the right answer is checkable):
- **Per field:** each of the five fields is compared with the expected value. A field the
  question doesn't ask for must be null. Where a question is honestly ambiguous, the
  dataset lists every acceptable value; for example, "my favourite mysteries" may or may
  not add `read`.
- **Author/title text:** counts as right if it finds the same books ("Le Guin" =
  "Ursula K. Le Guin").
- **Plan exactly right:** all five fields are right.
- **Right books returned:** the plan returns exactly the books a right plan returns.
- **Errors:** a timeout, provider error or unusable output counts as wrong.

**Cases (26):** plain and synonym genres ("whodunits", "historical fiction"), read status
("to-be-read pile"), ratings ("my favourite…", "3 stars or more"), tropes, including a
spelling variant ("slow-burn") and paraphrases ("political intrigue", "light and
comforting"), authors and titles, a three-filter combination, a trope the reader doesn't
have ("dragons"), no filter at all, and a prompt-injection attempt.

**Baseline:** `fake` is the offline keyword model (`AI_MODEL=fake`) used in tests and CI.
It shows what simple rules get right, and so what the LLM adds.

Reproduce (from `ai-service/`):

```bash
uv run python ../eval/run_eval.py --model fake
uv run --env-file ../.env python ../eval/run_eval.py --model anthropic:claude-haiku-5-5
# or, without a .env: export ANTHROPIC_API_KEY in this shell, then drop --env-file
uv run python ../eval/run_eval.py --report     # rebuilds the tables below
```

## Failure examples

- **`author-full`, "books by Ursula K. Le Guin" (Haiku):** the plan's explanation says
  "only the author name is used as a filter", but `text` came back empty, so the search
  returned all 16 books. The explanation also ends in a stray `"}`, so the model seems to
  have folded the rest of its structured output into the explanation string. The output
  is valid against `SearchPlan`, so nothing caught it.
- **`trope-mood`, "something light and comforting I haven't read" (Haiku):** it picked
  the right trope (`cozy`) and its explanation says "Unread books", but it left
  `read_status` empty. That's the same mismatch between explanation and filters, so it
  returned one book already read.
- **The keyword baseline** misses everything that needs understanding rather than
  matching: a spelling it has no rule for ("slow-burn" in front of "romances"),
  paraphrases ("political intrigue" → `politics`), and authors or titles that aren't
  written as "by X" ("do I have Dune?", "unread Agatha Christie").

## Conclusions

On this dataset, `claude-haiku-5-5` returned the right books for 24 of 26 questions
(92%), against 21 of 26 (81%) for the offline keyword model, with no errors or timeouts.
It got all genre, rating and trope fields right, including the spelling variant, a
paraphrase ("political intrigue" → `politics`) and the prompt-injection case. The gap is
smaller than it looks for two reasons. The keyword rules and the questions were written
by the same person, so the baseline is probably flattered. And with 26 cases, one case
is about 4 points, from a single run of a non-deterministic model. Both Haiku misses are
the same kind of bug: the explanation describes a filter that the structured fields
don't contain. That points to a concrete next step: an output-validator check that asks
the model to retry when the explanation mentions an author or "unread" but the matching
field is empty, or putting `explanation` before the filter fields so the model reasons
first. Haiku costs about 2.4 s per question, against effectively nothing for the keyword
model. For the app, that makes the LLM worth it for open-ended questions, while the
keyword model stays the right choice for tests, CI and key-less demos.
